# A. LLM 知识库与 RAG

## Q1. 从零构建一个 LLM 知识库，完整链路是什么？★★★ 高频

**参考答案**

```text
① 采集       原始文档（md/pdf/网页/代码注释）→ 统一成纯文本 + 保留结构（标题层级）
② 切块       按语义边界切（标题/段落/函数），不是按固定字数硬切
③ 向量化     用 embedding 模型编码成向量（并保留原文、来源、路径）
④ 索引       向量库（FAISS/Milvus/pgvector）+ 元数据（文件、章节、行号、更新时间）
⑤ 检索       混合检索：向量（语义）+ BM25（关键词）→ 融合
⑥ 重排       交叉编码器 rerank，取 top-k（k 一般 3~8）
⑦ 拼上下文   组装 prompt：指令 + 检索片段（带来源）+ 问题 + 输出格式约束
⑧ 生成       带上"必须引用来源、没有依据就说不知道"的约束
⑨ 评估       固定问答集：检索命中率 + 答案正确率 + 引用是否对得上
⑩ 迭代       失败的 case 回填成新的测试项，而不是只改 prompt
```

**面试时要强调的两点**：

1. **第②步是效果的天花板**。切块切坏了，后面再强的模型也救不回来（检索到半句话，模型只能编）。
2. **第⑨步决定它是不是"工程"**。没有固定评估集的 RAG 系统 = 每次改动全靠感觉。

**反问加分**：被问"你怎么保证质量"时，先问"这个知识库的**更新频率**和**误答代价**"——一次性文档和每天更新的运维手册，架构完全不同。

## Q2. 切块（chunking）怎么切？为什么它是效果上限？★★★ 高频

**参考答案**

**四种切法**：

| 方式 | 做法 | 适用 |
|---|---|---|
| 固定长度 | 按 token 数切，带 10%–20% 重叠 | 通用兜底 |
| 结构感知 | 按 Markdown 标题/HTML 层级切 | 文档、wiki |
| 语义切分 | 相邻句子 embedding 相似度骤降处断开 | 长文、无结构文本 |
| **代码感知** | 按函数/类/AST 节点切，保留签名 | 代码库、API 文档 |

**关键参数**：

- **块大小** 200–800 token：太小丢上下文（"见上文"指代不明），太大稀释语义（一块里混了三个主题，向量变成"平均"）。
- **重叠** 10%–20%：防止关键句被切断。
- **每个块带上"面包屑"**：`文件 > 章节 > 小节` 拼进文本再编码。这一条对中文技术文档效果提升最明显——很多块的正文只有"配置如下"，离开标题毫无检索价值。

```text
❌ 坏块：
  "配置如下：max_batch=32, timeout=30"

✅ 好块：
  "[PyTorch 部署手册 > 推理服务 > 超时设置] 配置如下：max_batch=32, timeout=30"
  ↑ 面包屑让这个块在检索"超时怎么设"时能被召回
```

**为什么是上限**：检索的本质是"用问题向量匹配块向量"。块的边界决定了"语义单元"的边界——**切错了，正确的答案就从来没以一个完整块的形式存在过**。

**追问**：*怎么判断切块好不好？* 拿一批真实问题，看"正确段落是否被召回"（检索命中率）。这一步比调模型有效得多。

## Q3. 向量检索和关键词检索，为什么要混合？★★☆

**参考答案**

| | 向量检索（dense） | 关键词检索（BM25/sparse） |
|---|---|---|
| 擅长 | 语义相近（"改学习率" ≈ "调 lr"） | **精确词**（函数名、错误码、版本号、专有名词） |
| 弱于 | 罕见专有名词、精确匹配 | 同义改写 |
| 例子 | 问"怎么让训练更稳"能召回"warmup 的作用" | 问 `CUDA error: an illegal memory access` 必须精确匹配 |

**混合方案**：

```text
dense_top50  ┐
             ├─→ RRF（Reciprocal Rank Fusion）融合 → rerank → top5
BM25_top50   ┘

RRF: score = Σ 1/(k + rank_i)，k 常取 60
```

**为什么用 RRF 而不是加权分数**：两路的分数尺度不可比（余弦相似度 0~1 vs BM25 无上界），加权要归一化、调参、且随语料漂移；**RRF 只用排名**，天然免疫尺度问题，且实验上很稳。

**追问**：*什么时候单用向量就够？* 纯语义问答（客服 FAQ）可以；**技术文档/代码库必须混合**——里面全是函数名、参数名、错误信息这些"语义无关但必须精确"的东西。

## Q4. 为什么要 rerank？它和向量检索的分工是什么？★★☆

**参考答案**

**分工**：

- **向量检索（bi-encoder / 双塔）**：问题和文档**分别**编码，可以离线建索引 → 快，适合从百万级里**粗筛** top-50~100。但它把整个文档压成一个向量，**细粒度匹配能力弱**。
- **rerank（cross-encoder / 交叉编码器）**：问题和文档**拼在一起**过模型，能建模词级交互 → 准，但**每个候选都要跑一次前向**，只能处理几十个。

```text
百万文档 ──向量检索──► top100 ──rerank──► top5 ──► LLM
           （快、粗）            （慢、准）
```

**成本权衡**（这题的重点是"知道代价"）：

- rerank 100 个候选 ≈ 100 次 BERT 前向，延迟增加 50–200ms（GPU 上）。
- 所以 **k 不能太大**。工程上常做"**两段式**"：先向量 top-100 → rerank → top-5 → 生成。
- 如果延迟敏感（线上对话），可能只 rerank top-20。

**追问**：*rerank 模型和 embedding 模型能共用吗？* 架构不同（双塔 vs 交叉），不能。但可以是同一家族的（如 BGE 的 embedding + BGE-reranker）。

## Q5. 怎么评估一个 RAG 系统？指标有哪些？★★★（工程能力的照妖镜）

**参考答案**

**必须分开评两段**（这是很多人漏的）：

```text
检索段：recall@k、MRR、nDCG       ← 正确段落有没有被捞上来
生成段：answer correctness、faithfulness（是否有编造）、citation accuracy（引用对不对）
```

**做法**：

1. **建一个固定问答集**（50–200 条），每条标好"标准答案 + 依据在哪个文件哪一节"。
2. 每次改切块/换模型/改 prompt，**跑同一套集**，看指标变化——不做这个，所有"效果变好了"都是错觉。
3. **错误归因**：答错时先判断是"**没检索到**"还是"**检索到了但答错**"。前者改检索，后者改 prompt/模型——**混在一起调，永远调不好**。

**低成本实现**：

```python
# 检索评测（不需要 LLM）
def recall_at_k(queries, gold_chunk_ids, retriever, k=5):
    hits = 0
    for q, gold in zip(queries, gold_chunk_ids):
        top = retriever.search(q, k=k)
        hits += bool(set(top) & set(gold))
    return hits / len(queries)
```

**追问**：*能用 LLM 当裁判吗？* 可以（LLM-as-judge），但要**抽检校准**——裁判本身有偏好（偏爱长答案、偏爱特定措辞），先用人工标 50 条对齐，再信它。

## Q6. 构建"LLM Wiki"和做普通文档有什么区别？★★☆（这题直接对应你的简历）

**参考答案**

普通文档是给人看的；**LLM Wiki 同时要给人看和给模型检索**，所以多出四个要求：

| 要求 | 具体做法 | 为什么 |
|---|---|---|
| **可切块** | 每个小节自成一体，标题写清"这是什么" | 检索按块召回，块不能依赖上文 |
| **可追溯** | 每条技术断言标出处（文档链接/论文/版本） | 模型会编，出处是唯一的纠错锚点 |
| **可增量** | 章节边界稳定，加内容不改结构 | 否则每次更新要重建全部索引 |
| **可判定** | 写清"适用版本/前提/反例" | 没有前提的断言在别处就是错的 |

**我自己的做法**（可以照这个讲）：

```text
每个知识点固定四段：
  ① 结论（一句话，能直接回答问题）
  ② 依据（为什么，含出处）
  ③ 反例/坑（什么时候不成立）
  ④ 版本/前提（PyTorch 2.x、OpenCV 4.4+ 等）

好处：
- 检索时"结论"这一段就能命中，不用召回整篇
- 模型引用时，出处和版本都在块内，不容易被误用
- 失效检测变简单：版本号变了就是待复查项
```

**反例（要避免的写法）**：

> "BN 的 momentum 一般设 0.1。"
>
> 问题：什么框架？什么版本？什么场景？小 batch 时还适用吗？——**没有前提的断言，检索出来就是误导**。

## Q7. 知识库怎么维护更新？怎么发现过时内容？★★☆

**参考答案**

**三个机制**：

1. **版本锚点**：每篇文档头部写"适用版本"。上游发版（PyTorch 2.4、OpenCV 4.10）时，按版本号筛出所有相关文档复查，而不是靠人记得。
2. **来源化**：每条断言指向原始出处。复查时先看**出处变没变**（官方文档改了没），比读全文快得多。
3. **失效信号**：
   - 检索日志里"命中但用户/模型答错"的 case → 内容可能已过时；
   - 文档里出现的 API 在最新版被 deprecated（可用脚本扫 API 名，比对 changelog）。

**增量索引**：切块按"文件名 + 章节 hash"做 ID，更新时只重建变化的块，不重建全库。这是让"知识库能长期活着"的关键——**全量重建的成本会让人放弃更新**。

**追问**：*怎么处理"同一问题的两种说法"？* 不要删，标**版本 + 适用条件**，让两者共存。知识库里"看起来矛盾"往往是因为前提不同，删掉一个反而丢信息。

## Q8. 上下文窗口怎么用？"塞越多越好"对吗？★★★

**参考答案**

**不对**。三个原因：

1. **lost in the middle**：模型对**开头和结尾**的信息利用最好，中间的长段容易被忽略（这与位置编码和注意力分布有关）。
2. **噪声稀释**：检索回来的无关片段会让模型分心，甚至把无关内容当依据——**精度随无关上下文增加而下降**。
3. **成本与延迟**：token 数与费用、延迟线性相关。

**工程做法**：

```text
① 检索 top-50 → rerank → 只取 top-3~5 塞进去
② 每段带来源标记，让模型能引用、你也能核对
③ 长文档先摘要再喂（但要保留原文可回溯，别只喂摘要）
④ 把"最重要的约束"放在 prompt 的**开头和结尾**（系统提示 + 结尾重申）
⑤ 超出窗口时：分块处理 + 汇总，或"先检索再生成"（RAG 而非长上下文）
```

**一个具体技巧**：把"输出格式要求"放在**最后一句**，比放在开头更管用（模型对最近指令的遵守率更高）。这条在让模型输出 JSON 时特别明显。

**追问**：*长上下文模型（128k/1M）还需要 RAG 吗？* 需要。长上下文解决的是"一次能看多少"，RAG 解决的是"该看哪些"——**在 100 万 token 里找一个答案，比在 5 个片段里找，准确率更低且更贵**。

# B. 任务拆解与计划书

## Q9. 拿到一个模糊需求，怎么用 LLM 做任务拆解？★★★ 高频

**参考答案**

**核心原则：先对齐"完成"的定义，再拆步骤**。否则拆出来的是一堆"看起来像活的活"。

```text
① 澄清（我自己做，不交给模型）
   - 输入是什么？输出是什么？谁用？验收标准是什么？
   - 边界：哪些不做？（明确"不做"比"做什么"更能防跑偏）

② 让模型产出"候选拆解"，我改
   提示词要点：给定上下文 + 约束（技术栈/时间/不能改的文件）+ 要求输出
   "阶段 → 每阶段的产物 → 验收命令"

③ 我逐条审查三件事
   - 顺序对不对（有没有前置依赖被漏掉）
   - 每步是否**可独立验证**（不能验证的步骤要再切）
   - 有没有"隐形大步骤"（比如"实现检测后处理"其实包含 NMS+阈值+坐标还原）

④ 落成计划书（文件，不是聊天记录）
   每步写：改哪个文件、改哪个函数、输入输出、边界条件、验收方式
```

**好拆解的标准**（可以背下来）：

> **每一步都能单独跑一个命令或写一个断言来证明它对了。**

不满足这条，说明还得再切。

**反例**：让模型"帮我实现一个缺陷检测系统"——它会给你一份看起来很完整的架构，但每一条都无法直接执行。**问题不在模型，在提问**。

## Q10. 怎么给 LLM 写"计划书"级别的提示，让它一次做对？★★★

**参考答案**

**五个必备成分**（缺一个，返工率明显上升）：

```text
1. 角色与目标      "你在一个 PyTorch 检测项目里，目标是把 NMS 从 Python 换成 CUDA 版"
2. 上下文事实      文件路径、关键函数签名、数据结构、现有约定（不要让它猜）
3. 硬约束          不能改的接口/不能引入的依赖/必须保持的行为
4. 输出格式        改哪些文件、给完整函数还是 diff、要不要写测试
5. 验收标准        跑什么命令、期望什么输出
```

**一个可复用的模板**：

```markdown
## 任务
把 `postprocess.py::nms()` 的 Python 实现替换为 torchvision.ops.nms，保持函数签名不变。

## 现状
- 函数签名：`def nms(boxes: Tensor[N,4], scores: Tensor[N], iou_thr: float) -> Tensor`
- boxes 是 xyxy 格式、已按分数降序
- 现有单测：`tests/test_post.py::test_nms_basic`（必须仍然通过）

## 约束
- 不改签名、不新增依赖（torchvision 已在 requirements）
- 空输入 `N==0` 必须返回空 tensor，不能抛异常

## 输出
1. 修改后的完整函数
2. 新增单测：空输入、全重叠、无重叠 三种情况
3. 一句话说明行为差异（如果有）

## 验收
`pytest tests/test_post.py -q` 全绿
```

**为什么这样有效**：把"猜"的空间压到最小。模型出错最多的地方不是"不会写代码"，而是**缺少上下文**（不知道你的 boxes 是什么格式）→ 于是它编一个。

**追问**：*要不要让模型先复述需求？* 要，尤其是复杂任务：让它先输出"我理解的约束和验收标准"，你确认后再动手。**这一步能省掉 80% 的返工**。

## Q11. 大任务怎么防止"越做越偏"？★★☆

**参考答案**

**四个机制**：

1. **锚点文件**：把目标、约束、验收标准写进一个文件（`TASK.md` / `AGENTS.md`），每次对话**先让它读**。上下文被压缩或换会话时，这个文件是唯一不丢的东西。
2. **小步提交**：一步一改，每步能回滚。不要"一次让它重构三个模块"——出错时你不知道是哪一步坏的。
3. **阶段性验收**：每完成一步就跑测试/看输出，**不要攒到最后**。攒到最后的代价是：错误已经互相掩盖，定位成本翻倍。
4. **定期回读锚点**：做完 3–4 步后，让它对照 `TASK.md` 自查"当前进度 / 偏离 / 遗留"，比你自己翻记录快。

**一个真实的失败模式**（可以讲）：

> 让它"优化推理速度"，它开始改预处理、改模型、改后处理，每一步都"合理"，但整体偏离了"只优化后处理"的原始目标，最后 diff 有 800 行没法 review。**根因是没有锚点文件 + 没有阶段性验收**。

## Q12. 怎么把"知识库"接进开发流程？★★☆（结合你的课设/工作讲）

**参考答案**

三种接法，按侵入性递增：

| 方式 | 做法 | 适用 |
|---|---|---|
| **被动查询** | 人工把检索结果贴进对话 | 起步阶段，验证知识库质量 |
| **工具调用** | 给模型一个 `search_docs(query)` 工具，它自己决定何时查 | 主流做法（function calling / MCP） |
| **自动注入** | 按当前文件/报错自动检索相关文档，作为上下文前置 | 深度集成，需要好的触发规则 |

**关键设计**：

1. **返回结果必须带来源**（文件名 + 章节 + 行号），模型才能引用，你才能核对。
2. **检索失败要显式返回"没找到"**，而不是返回最相似的垃圾——否则模型会拿垃圾当依据编。
3. **设"必须查"的触发条件**：涉及具体 API/版本/配置时强制检索，避免模型凭记忆答（它的记忆可能是几年前的）。

**追问**：*知识库要不要包含代码本身？* 要，但要**索引函数签名 + docstring + 调用示例**，而不是整份源码（源码块太大、语义被稀释）。

---

## Q13. 用 LLM 写代码，怎么保证"能维护"而不只是"能跑"？★★☆

**参考答案**

**四条纪律**：

1. **一次只让它改一个函数/一个文件**。跨文件的改动由你主导——它能写对局部，但很难理解你项目里的隐式约定。
2. **接口先定，实现后填**。你先写签名 + docstring + 测试，让它填实现。这样它不会顺手改你的架构。
3. **要求它解释"为什么"**，不只是给代码。解释里出现"假设…"的地方，就是你需要核对的地方。
4. **风格一致性**：把项目里一个**已有文件**贴给它当范例（"照这个文件的风格写"），比写十条规则管用。

**判断它写的代码是否可信的三个信号**：

- 它引用的 API 你能在官方文档里查到（**查不到就是编的**）；
- 它写的边界条件（空输入、单元素、越界）你能想到；
- 它能解释异常路径（失败了会怎样）。

**反例**：它给你一段用了 `torch.cuda.amp.GradScaler()` 的代码——能跑，但那是旧接口（2.4 起推荐 `torch.amp.GradScaler("cuda")`）。**它的训练数据有滞后，这是系统性风险，不是偶发。**

## Q14. 提示词工程里，哪些技巧是真的有用、哪些是玄学？★★☆（判断力题）

**参考答案**

**确实有效**（有稳定的机制解释）：

| 技巧 | 为什么有效 |
|---|---|
| **给示例（few-shot）** | 把"格式/风格/边界"从抽象描述变成具体模式 |
| **明确输出格式 + schema** | 减少歧义，可程序化校验 |
| **先复述再执行** | 强制模型对齐理解，暴露偏差 |
| **分步思考（复杂推理）** | 给模型中间计算的空间；但**简单任务上反而增加出错面** |
| **把关键约束放开头和结尾** | 位置效应（首尾利用最好） |
| **要求引用来源** | 让"编"变得有成本，提升可核查性 |
| **提供反例**（"不要像这样"） | 比只说"要怎样"更能划定边界 |

**接近玄学**（效果不稳定/不可复现）：

- 各种"魔法咒语"（"深呼吸""你是世界最好的专家"）——在**新模型上收益很小**，且不可控；
- 精确到小数点的"温度必须 0.73"——没有可解释的机制；
- 超长的人设描述——占 token，收益递减。

**判断标准**（这是回答的落点）：

> "我只保留**能在自己任务上稳定复现收益**的技巧，并且用固定测试集验证。凡是"据说有效"但我复现不出来的，我就不写进团队规范——否则会给别人制造假因果。"

# C. 代码开发与评审

## Q15. 让 LLM 写代码，最常见的失败模式有哪些？★★★ 高频

**参考答案**

按"危害程度"排序：

| 失败模式 | 表现 | 防御 |
|---|---|---|
| **幻觉 API** | 调用不存在的函数/参数（`cv2.someNewThing()`） | **逐个 API 去官方文档核对**，尤其新版本特性 |
| **版本滞后** | 用已废弃接口、旧写法（`torch.cuda.amp`、`np.float`） | 在 prompt 里写明版本；或让它先列"要用到的 API 及版本" |
| **静默行为变更** | 顺手改了默认参数、异常处理、返回类型 | **要求 diff + 逐行 review**，重点看"没被要求却改了的地方" |
| **过度设计** | 你要个函数，它给你一个类 + 工厂 + 配置系统 | 明确"最小实现""不要引入新抽象" |
| **测试造假** | 写的测试断言 `assert True`，或 mock 掉了被测逻辑 | 看测试是否**能在改坏代码时失败**（做一次变异验证） |
| **安全/性能陷阱** | 用 `eval`、字符串拼 SQL、O(n²) 循环处理大图 | 代码评审清单（Q17） |
| **依赖引入** | 悄悄 `pip install` 一个新库 | 明确"不许新增依赖"，review `requirements` |

**一句话总结**：

> "它很少写出**语法错误**的代码，但很容易写出**语义错误**的代码。所以我的 review 重点不是"能不能跑"，而是"**行为是不是我想要的**"。"

---

## Q16. 你怎么 review LLM 生成的代码？有清单吗？★★★

**参考答案**

**五层清单**（按顺序，逐层过滤）：

```text
① 能不能跑         ── 语法/导入/形状
② 行为对不对       ── 边界条件：空输入、单元素、极值、NaN、设备不一致
③ 有没有偷改       ── diff 里"我没要求"的改动（默认值、异常、日志、返回类型）
④ 接口一致性       ── 命名/参数顺序/错误处理风格是否和项目一致
⑤ 有没有更简单的写法 ── 它是不是引入了不必要的抽象/依赖/复杂度
```

**我必查的五个具体点**：

1. **数值边界**：除零、`log(0)`、`sqrt(负数)`、`int` 溢出、`uint8` 回绕。
2. **设备/精度**：张量在不在同一 device、dtype 是否一致（CPU 上跑通、GPU 上炸是最常见的）。
3. **异常路径**：失败时是抛异常还是返回 None？调用方有没有处理？
4. **资源**：文件/句柄/CUDA 显存有没有释放（`with`、`try/finally`）。
5. **可测试性**：这段代码能不能被单测覆盖？不能的话先重构再合并。

**一个具体习惯**：

> 让它把改动**按"行为变化"列成条目**（"改了什么、影响哪些调用方"），而不是只给 diff。这个列表能立刻暴露"它自己也没意识到的改动"。

---

## Q17. LLM 写的测试怎么判断靠不靠谱？★★☆

**参考答案**

**核心检验：变异测试（mutation）**——故意把被测代码改坏，看测试会不会失败。

```python
# 它给你这个测试
def test_nms():
    boxes = torch.tensor([[0,0,10,10],[1,1,11,11]], dtype=torch.float)
    out = nms(boxes, torch.tensor([0.9, 0.8]), 0.5)
    assert out.shape[0] == 1

# 检查：把 nms 的阈值逻辑改坏（写成 iou <= thr 的反向），测试还过不过？
# 如果还过 → 这个测试没测到关键逻辑
```

**其他红旗**：

- 断言太弱（`assert result is not None`）；
- **mock 掉了被测逻辑本身**（测了个寂寞）；
- 只测 happy path，没有边界；
- 覆盖率很高但断言很少（**覆盖率不等于有效性**）。

**我的做法**：要求它给的每个测试都**至少有一个"会失败的版本"**——它得能说出"如果这段逻辑写错，哪个断言会挂"。说不出来，这个测试就是装饰品。

## Q18. 用 LLM 做代码重构，边界在哪？★★☆

**参考答案**

**适合交给它的**：

- 机械性重构：改名、提取函数、拆长函数、统一日志格式；
- 有明确模式的转换：`for` 循环改写为向量化、同步改异步；
- 补测试、补类型注解、补 docstring。

**不适合单独交给它的**：

- **改架构/模块边界**（它看不到全局依赖）；
- **并发/生命周期相关**（引用计数、锁顺序、异步取消——它容易写出"看起来对"的竞态）；
- **性能关键路径**（它倾向写"正确但慢"的代码，比如 Python 循环）；
- **涉及外部协议/硬件**的改动（寄存器、时序、字节序）。

**一条实用规则**：

> **"作用域不超过一个文件 + 有测试兜底"**的重构交给它；超出的我写计划书，让它按步执行，每步我验收。

## Q19. 怎么让 LLM 理解一个陌生的老代码库？★★☆

**参考答案**

**别让它"读全库"**（既贵又容易被无关细节淹没）。用"**从入口往下钻**"的方式：

```text
① 先要一张地图：目录树 + 每个目录一句话职责（它读 README/文件头就能给）
② 定位入口：main / 服务的 handler / 训练脚本 → 顺着调用链往下
③ 每次只问一个具体问题："这个函数被谁调用""这个全局变量在哪赋值"
④ 让它输出"调用关系 + 文件:行号"，而不是复述代码
⑤ 关键处我自己打开文件核对（它的行号经常对不上）
```

**能显著提升效果的三个上下文**：

1. **一份已知正确的示例**："这是项目里另一个模块的写法，请照这个风格分析"；
2. **构建/测试命令**（它不知道你怎么跑测试，就会瞎猜）；
3. **约束文件**（`AGENTS.md` / `.cursor/rules/`）——把"这个项目是什么、不能碰什么"固化下来，每次对话都生效。

**追问**：*怎么防止它"编造行号"？* 让它引用时用**函数名 + 代码片段**而不是行号；行号由你或工具去定位。

## Q20. AI 辅助开发对团队协作有什么影响？怎么落地成规范？★★☆

**参考答案**

**正面**：样板代码、测试、文档的产出速度显著提升；新人上手快（可以问"这段为什么这么写"）。

**负面（必须管理）**：

1. **代码同质化 + 无人理解**：能跑但没人知道为什么这么写 → **要求提交说明写"为什么"，不只是"改了什么"**。
2. **review 负担转移**：生成快、审查慢，瓶颈从"写"变成"读" → 需要**更小的 PR**、更明确的验收标准。
3. **风格漂移**：每个人用不同提示词 → 产出风格不一 → 需要**项目内的规则文件 + 示例文件**。
4. **知识泄漏**：把内部代码贴进外部服务 → 需要明确的**数据边界政策**。

**落地规范（三件套）**：

```text
① 项目规则文件（AGENTS.md / rules）：
   技术栈、目录职责、构建与测试命令、禁止事项、代码风格样例
② 提交规范：
   AI 参与的改动要在 PR 描述里注明"哪部分由 AI 生成、如何验证"
③ 验收规范：
   新代码必须有测试；关键路径必须有数值对齐（如 max abs diff）
```

**一句话**：**"AI 提高的是产出速度，不是可信度。所以流程要加在'验证'那一侧，而不是'禁止'那一侧。"**

## Q21. 你怎么衡量"用 AI"到底有没有提效？★★☆（防吹牛题）

**参考答案**

**别用"感觉快了 50%"**，用可测量的三个指标：

| 指标 | 怎么测 | 注意 |
|---|---|---|
| **任务周期** | 同类任务（如"加一个数据增强"）用/不用 AI 的耗时 | 要同类任务，否则不可比 |
| **返工率** | 生成代码被 review 打回的比例 | 这个指标往往最能说明问题 |
| **缺陷密度** | 每千行新增代码的 bug 数（上线后统计） | 提效但引入 bug 是负收益 |

**反直觉的结论（可以说，会加分）**：

> "在**我很熟**的领域，AI 提效有限——因为我知道怎么写，review 它反而费时间；在**我不熟**的领域（比如某个新库的 API），它省的时间最多，但**出错的风险也最高**。所以我的用法是：熟悉的领域让它写样板和测试，陌生的领域只让它给'方向和选项'，代码我自己写。"

# D. Bug 排查

## Q22. 遇到一个 bug，你会怎么用 LLM 排查？★★★ 高频（最能体现经验）

**参考答案**

**关键是"你给的信息质量"，不是"模型的聪明程度"**。

```text
① 先自己复现 + 缩小范围（这一步不能省）
   - 能稳定复现吗？最小复现是什么？
   - 二分：注释掉一半、换输入、降版本

② 给它"四件套"
   - 完整报错（含 traceback 最后 5 层 + 版本号）
   - 最小复现代码（能跑的那种，不是整个项目）
   - 相关代码片段（出错的函数 + 调用方）
   - 我已经排除的可能（"不是显存问题，nvidia-smi 正常"）

③ 让它给"假设清单 + 验证方法"，而不是直接给答案
   要求输出："可能原因（按概率）｜如何验证｜验证结果意味着什么"

④ 逐条验证，把结果反馈给它
   - 排除的要说"已排除，因为…"，否则它会反复提同一个

⑤ 定位后要"根因"，不是"绕过"
```

**为什么第③步重要**：直接要答案，它会给你最"常见"的原因（往往不是你的）；要**可验证的假设**，你就在做真正的二分排查。

**一个模板**：

```markdown
现象：训练第 300 步 loss 变 NaN
环境：PyTorch 2.3, CUDA 12.1, A100, batch=8, AMP fp16
已排除：数据无 NaN（已 assert）、lr 已降 10 倍仍复现
代码：[出错的 loss 函数]
问题：给出 5 个最可能的原因，每个附一个"最小验证方法"，按验证成本排序
```

## Q23. LLM 排查 bug 时最容易犯什么错？怎么防？★★☆

**参考答案**

| 错误 | 表现 | 防御 |
|---|---|---|
| **过度自信** | "问题就是 X"（其实是猜的） | 要求它给**置信度 + 验证方法**，别只给结论 |
| **锚定第一个假设** | 你说"我怀疑是 A"，它会一路论证 A 对 | **别提你的猜测**，先让它独立分析，再对比 |
| **建议"绕过"而非"修复"** | "加个 try/except 就好了" | 明确要求"根因 + 为什么" |
| **版本错配** | 按旧版本 API 解释你的报错 | 报错里带版本，或让它先问版本 |
| **复现不了却给方案** | 没看到最小复现就开始改 | **先要求它复述现象**，错了你纠正 |

**最有效的防御**：

> "我每次都会让它**先说'我需要哪些信息才能确定'**。它列出来的缺项，往往就是我自己没想清楚的地方——这一步经常直接让我找到问题。"

## Q24. 一个"AI 改了三版还是不对"的 bug，你怎么收场？★★☆（抗压题）

**参考答案**

**先止损，再换策略**：

```text
① 停止迭代：回滚到已知可用的版本（不要在被改乱的代码上继续改）
② 自己读代码：把出问题的 30 行完整读一遍（很多时候这一步就够了）
③ 换视角，不换模型：
   - 让它"解释这段代码在做什么"（而不是"修它"）→ 经常在解释时暴露矛盾
   - 让它"写出这段代码的前置条件/后置条件"→ 不变式往往就是 bug 所在
   - 让它"列出这段代码的 5 个可疑点"，你挑
④ 加观测：打日志、断言、最小单测，把"猜"变成"看"
⑤ 承认边界：如果它连续两轮都在同一个错误假设上打转，说明信息不够或问题超出它的能力——手工调试更快
```

**一句话（可以背）**：

> "AI 排查的价值在**前 30 分钟**（快速给出假设空间）；如果卡住了，它的价值会**迅速下降**——因为它没有运行时信息。这时候人的观测能力（断点、打印、profiler）是不可替代的。"

## Q25. 怎么让 bug 排查"可复用"？★★☆

**参考答案**

**把每次排查变成资产**：

1. **错误 → 根因 → 修复** 写成条目（追加到项目的 troubleshooting 文档）；
2. 条目格式固定：**现象 / 环境 / 根因 / 修复 / 如何验证 / 如何预防**；
3. 同一类错误出现第二次时，**加断言或加测试**，让它不可能再发生（而不是再查一遍）。

```markdown
## NaN at step 300（AMP）
- 现象：loss 突然 NaN，无报错
- 环境：PyTorch 2.3 + fp16 + A100
- 根因：focal loss 里 log(p) 在 p=0 时 → -inf
- 修复：p.clamp_min(1e-7) 再取 log
- 验证：单测构造 p=0 的输入
- 预防：所有 log/sqrt/div 统一走 `safe_log` 工具函数
```

**为什么这题重要**：面试官想听的不是"我怎么查 bug"，而是"**你怎么让同一个 bug 不查第二遍**"——这是工程成熟度的标志。

---

## Q26. 怎么排查"只在生产环境出现"的问题？★★☆

**参考答案**

**核心方法：把生产的信息搬回来，而不是把代码搬到生产去试**。

1. **固化现场**：日志（结构化）、输入样本（脱敏保存）、环境快照（版本/驱动/GPU 型号）、指标（延迟/显存/温度）。
2. **本地复现**：用生产的那份输入 + 尽量一致的版本。**80% 的"只在生产出现"是版本或数据差异**。
3. **差异清单**：它帮你列"本地 vs 生产可能不同的所有点"（库版本、编译选项、并发度、batch 组成、预处理路径），逐项排除——这个清单它列得比你全。
4. **假设驱动**：按"最可能且最便宜验证"的顺序排。

**典型根因（可以举）**：

- 预处理不一致（训练用 BGR、线上用 RGB）→ 专题二 Q36；
- 精度差异（线上 fp16、线下 fp32）；
- 并发下的竞态（本地单线程不复现）；
- 数据分布漂移（线上出现训练时没见过的光照/背景）。

## Q27. 让 LLM 读日志/堆栈，怎么给才有效？★★☆

**参考答案**

**给"结构"，不给"全文"**：

```text
❌ 贴 5000 行日志
✅ 贴：
   1. 报错的关键 20 行（含异常类型 + 最后一层业务代码）
   2. 出错前后的 3 条关键日志（时间、线程、请求 ID）
   3. 相关配置（batch、线程数、超时）
   4. 你说的"正常时"长什么样（对照组）
```

**技巧**：

- **先让它提取模式**："这三段日志的差异是什么"——比让它"分析原因"更容易得到有用输出；
- **时间对齐**：多线程日志要带时间戳和线程 ID，否则它会编出一个不存在的因果链；
- **别贴敏感信息**（密钥、路径带用户名、内部 IP）。

**追问**：*日志太长必须贴怎么办？* 先做**结构化摘要**（按错误类型计数、按时间段聚合），再贴摘要 + 少量原始样本。

# E. 回归测试与质量门

## Q28. 什么是"回归测试集"？CV 项目里具体长什么样？★★★ 高频

**参考答案**

**定义**：一组**固定输入 + 固定预期**的用例，每次改动后跑一遍，保证"没把已经对的东西改坏"。

**CV 项目的四层**（从便宜到贵）：

```text
① 单元测试      纯函数：NMS、坐标变换、IoU、数据增强的可逆性
                断言：具体数值（用 tolerance）

② 数值对齐测试  导出 ONNX/TRT 后，和 PyTorch 输出逐层对比
                断言：max abs diff < 1e-4（fp32）/ < 1e-2（fp16）

③ 端到端金标准  一批固定图片 + 人工确认过的结果
                断言：检测框数量、类别、关键框的 IoU > 0.9

④ Bad case 集   历史上出错过的样本（漏检/误检/崩溃）
                断言：这些样本现在必须对（或至少不再崩）
```

**关键设计**：

1. **金标准集要小**（20–100 条），小到能每次跑、小到有人愿意维护；
2. **每条用例要写"为什么在这"**，否则半年后没人敢删；
3. **bad case 只增不删**（除非确认场景已废弃），它是你交过学费换来的。

**追问**：*模型升级后精度提升了，回归测试却挂了，怎么办？* 这说明**预期值需要更新**——但要**逐条看差异**，确认是"变好了"还是"变坏了"。直接批量更新预期值是最危险的操作（等于把测试废掉）。

## Q29. CV 模型的回归测试和普通软件有什么不同？★★☆

**参考答案**

| 维度 | 普通软件 | CV 模型 |
|---|---|---|
| 输出 | 确定值 | **浮点 + 概率**，天然有波动 |
| 断言 | 相等 | **容差范围**（数值）+ **指标阈值**（精度） |
| 非确定性 | 少 | 训练随机性、GPU 算子非确定性、数据增强 |
| "正确"的定义 | 明确 | **依赖业务**（漏检 vs 过杀哪个更贵） |
| 数据 | 代码 | **数据本身也是一等公民**（要版本化） |

**因此 CV 回归测试要多做三件事**：

1. **固定随机性**（seed、deterministic 算法）——否则测试本身就是噪声源。但注意：**确定性 ≠ 跨硬件一致**（不同 GPU 型号仍可能差）。
2. **数据版本化**：数据集 hash / DVC / 清单文件。**没有数据版本，回归测试无法复现**。
3. **分片指标**：不只看总 mAP，要看**按类别/尺寸/批次**切片——整体持平的模型，可能在某个关键类别上崩了。

**追问**：*数值容差怎么定？* 按"业务能容忍的误差"倒推。分类概率差 1e-3 无所谓；但框坐标差 1 像素可能影响测量——所以**检测的回归测试要断言框的 IoU，而不是分数相等**。

## Q30. 怎么给模型迭代设计"质量门"（gate）？★★☆

**参考答案**

**三道门，任何一道不过就不许上**：

```text
门 1（自动，分钟级）：单元 + 数值对齐 + 端到端金标准
   → 挂了直接打回，不需要人看

门 2（半自动，小时级）：固定评测集的业务指标
   → 漏检率、过杀率、按类别切片、P99 延迟
   → 设"不许变差"的底线 + "变好幅度"的门槛（防噪声）

门 3（人工，天级）：bad case 抽检 + 灰度
   → 抽 50 张线上真实图，人工确认
   → 灰度 1–5% 流量，看线上指标
```

**关键细节**：

- **门 2 的阈值要防"指标噪声"**：mAP 差 0.2% 可能只是随机种子不同。要让结论可信，要么多 seed 平均，要么只看**超过阈值的差异**。
- **门 3 不能省**：自动指标过了但人工抽检发现"框的位置偏了"这类问题，只有人眼能发现。

## Q31. 数据本身怎么回归测试？★★☆（容易被忽略）

**参考答案**

模型回归之外，**数据管线也要有测试**。CV 里数据 bug 比模型 bug 更常见、更隐蔽。

```python
# 数据管线的断言清单
assert 0 <= img.min() and img.max() <= 255 or img.dtype == np.float32
assert boxes[:, 2] > boxes[:, 0] and boxes[:, 3] > boxes[:, 1]     # 宽高为正
assert (boxes[:, 0] >= 0).all() and (boxes[:, 2] <= W).all()        # 不越界
assert labels.max() < num_classes and labels.min() >= 0
assert masks.shape == (H, W)
```

**要测的**：

1. **增强的可逆性**：翻转 + 翻转 = 原图；仿射变换后**框也要跟着变**（这是最常错的地方）。
2. **归一化参数**：训练/验证/推理必须**同一套** mean/std。
3. **类别映射**：label id ↔ 类别名 的映射，训练和推理必须一致（错一个 id，某类全错）。
4. **切分泄漏**：train/val 之间不能有同一批次/同一原图的裁剪。

**追问**：*怎么测"切分没泄漏"？* 按**原图 ID 或采集批次**分组切分，然后断言两组的 ID 集合交集为空。图片级切分而同一张图裁成多个 patch 是典型泄漏。

## Q32. 用 LLM 生成回归测试，怎么保证覆盖到你关心的边界？★★☆

**参考答案**

**别让它自由发挥**，给它**边界清单**让它填：

```markdown
请为 `letterbox_resize(img, target)` 写测试，必须覆盖：
1. 宽 > 高（横向图）
2. 高 > 宽（纵向图）
3. 正方形
4. 极小图（1×1）
5. 极大缩放比（100×）
6. 输入已经是目标尺寸（应保持不变，不重复 padding）
7. 通道数不是 3（应报错）
边界值依据：目标尺寸固定 640×640，padding 值 114
```

**为什么这样有效**：LLM 自己想边界时，倾向于给"典型值"（正方形、正常尺寸），**恰恰漏掉最容易出错的极端情况**。你把边界列出来，它负责写代码——分工明确。

**追问**：*生成的测试要不要全收？* 不。只保留**能在代码写错时失败**的（见 Q17 变异测试）；重复的、断言弱的删掉，否则测试集变成负担。

# F. 风险、边界与话术

## Q34. LLM 会幻觉，工程上怎么防？★★★ 高频

**参考答案**

**分三层防**（缺一层都不够）：

```text
① 输入层：给它依据
   RAG 检索 + 强制"只基于给定材料回答"
   —— 但注意：有材料它也可能不看，所以要强制引用

② 生成层：让"编"有成本
   要求每条结论标注来源（文件/章节/行号）
   允许说"不知道"（明确写进 prompt：没依据就回答"未找到"）

③ 输出层：程序化校验
   引用是否存在于检索结果里（字符串匹配/ID 校验）
   代码是否可运行（跑一遍）
   数值是否在合理范围（断言）
```

**对代码场景的特殊防御**：**幻觉 API 只能靠外部核对**——让它列出用到的所有 API，你逐个查官方文档。这一步不能省，因为代码"看起来对"的迷惑性最强。

**追问**：*降低 temperature 能减少幻觉吗？* 能减少**随机性**，但不能消除**知识性幻觉**（它不知道的东西，温度 0 也会编）。真正的解法是**给它依据 + 校验输出**。

## Q35. 用外部 LLM 服务，数据安全怎么考虑？★★☆

**参考答案**

**分级处理**：

| 数据级别 | 例子 | 处理 |
|---|---|---|
| 公开 | 开源代码、公开论文 | 随便 |
| 内部 | 项目代码、设计文档 | 看公司政策；优先用**私有部署/企业版**（承诺不训练） |
| 敏感 | 客户数据、产线图像、密钥、个人信息 | **不出内网**；必须用时做脱敏/构造等价样例 |

**具体做法**：

1. **脱敏**：路径去用户名、IP/域名替换、密钥用占位符、图像换成合成图。
2. **最小化**：只贴相关的那 50 行，不贴整个仓库。
3. **可审计**：团队约定"哪些服务可用、哪些数据不能进"，写进规范。
4. **代码场景的额外风险**：贴进去的代码可能被用于训练 → 反过来影响你的**知识产权**。

**追问**：*本地模型能替代吗？* 敏感场景值得（成本换安全），代价是能力弱一档——通常用于"补全/格式化/简单重构"，复杂任务仍要人做。

## Q36. 怎么判断"这个任务该不该用 LLM"？★★★（判断力题）

**参考答案**

**该用**（特征：模式明确 + 可验证 + 重复）：

- 有明确输入输出、能写断言验证的（转换、重构、补测试、写样板）；
- 需要快速进入陌生领域的"方向感"（有哪些方案、各自代价）；
- 文本类吞吐（文档、注释、commit message、review 意见初稿）。

**不该用 / 慎用**（特征：不可验证 + 高耦合 + 高代价）：

- **无法自动验证**的正确性（架构决策、性能调优的根因、并发正确性）；
- **需要全局上下文**的改动（跨模块重构、接口演进）；
- **错误代价极高**的（生产数据迁移、安全相关、医疗/金融决策）；
- **需要真实运行信息**的（线上性能问题、竞态、内存泄漏）。

**判断口诀**：

> "**能不能用一条命令/一个断言证明它对？** 能 → 大胆用；不能 → 只用它给候选，判断自己做。"

## Q37. 面试官问"你用 AI 提效了多少"，怎么答才可信？★★★（话术题）

**参考答案**

**别说百分比，说"改变了什么"**。给三档答案，按你实际情况选：

**（a）最稳的答法——说流程变化**：

> "我把'写代码'的时间压下来了，但'定义问题和验收'的时间上去了。净效果是**迭代次数变多**——以前一周做一次实验，现在能一天跑两三次。这个变化比'提效 50%'更真实，也更好衡量。"

**（b）有数据时的答法**：

> "同类任务（加一个数据增强 + 补测试）我从半天降到 1–2 小时；但**返工率大概 20%**——主要是它不理解我们项目的隐式约定。所以我给它定了'接口我先写、实现它来填'的规矩，返工率降下来了。"

**（c）承认边界的答法（最加分）**：

> "在我不熟的领域它省时间最多，但也最容易骗我——比如它会用已废弃的 API，而且代码看起来完全正常。所以我现在有个硬规矩：**它给的每个 API 我都要去官方文档核一遍**。这条规矩让我的'提效'打了个折，但避免了那种'跑通了、上线才炸'的事故。"

**为什么这样答可信**：主动给出**代价和失败案例**，比一味说好更让人信；而且展示了你有**自己的方法论**。

## Q38. 这个岗位为什么要问 AI 辅助编程？你理解它在考察什么？★★☆（元问题）

**参考答案**

**我认为在考察四件事**（这个回答本身就展示了你对岗位的理解）：

1. **工程素养**：有没有"验证"的习惯。AI 让写代码变便宜，**让验证变贵**——没有测试/回归意识的人，用 AI 只会更快地产生垃圾。
2. **判断力**：知道什么该交出去、什么必须自己做。这是区分"会用工具"和"被工具带跑"的分界线。
3. **可复现性**：他的产出是不是"凭手气"。有流程（锚点文件、分步验收、固定测试集）的人，质量是稳定的。
4. **对边界的诚实**：会不会为了显得厉害而夸大。**能说清"它哪里不行"的人，通常是真的用过。**

**我的看法**（可以照说）：

> "AI 辅助编程改变的是**成本结构**，不是**正确性标准**。写代码便宜了，所以'想清楚要什么'和'验证对不对'变得更值钱。我在项目里做的所有规范，都是围绕这两件事——而不是围绕'怎么让 AI 多写点'。"

# G. 快问快答（45 题）

> 一题一行结论。RAG/检索 18 题 + 提示与调用 12 题 + 工程化 15 题。

**Q39** `temperature` 在做什么？ —— 在 softmax 前除以 `T`：`T→0` 分布变尖锐（几乎总选最高分）、`T>1` 更随机。**它只影响采样，不影响模型"知不知道"**——所以降温度不能消除知识性幻觉。

**Q40** `top_p` 和 `top_k` 的区别？ —— `top_k` 固定保留概率最高的 k 个候选；`top_p`（核采样）保留**累积概率达到 p** 的最小集合（集合大小随分布自适应）。**通常只调其中一个**，同时调会互相干扰。

**Q41** 中文的 token 怎么估算？ —— 大致 **1 个汉字 ≈ 1 token**、**1 个英文单词 ≈ 1.3 token**、代码里符号和短标识符各算 1 个。粗估上下文用量够用，**精确计费要看 API 返回的 usage**。

**Q42** few-shot 给几个例子合适？ —— 3–5 个足够拉开效果，再多收益递减且占 token。**例子的"多样性"比数量重要**——覆盖边界情况（空输入、异常格式）的例子最值钱。

**Q43** 系统提示和用户提示的优先级？ —— 系统提示是"长期约束"（角色、安全边界、输出格式），用户提示是"本次任务"。**冲突时以系统提示为准**，但实际模型对"最近的指令"更敏感——所以关键约束**在用户消息末尾重申一遍**更保险。

**Q44** 结构化解耦（JSON mode / schema）为什么重要？ —— 让输出**可程序化校验**，而不是靠正则解析自然语言。**但要注意**：模型可能输出"合法 JSON 但语义错"（字段对、值编造），schema 只保证格式。

**Q45** function calling 的机制是什么？ —— 你把工具描述（名字、参数 schema）发给模型，模型**不执行**，只返回"要调用哪个工具、参数是什么"；你执行完把结果作为新消息发回去。**执行权在你手上**，这也是安全边界。

**Q46** MCP 解决什么问题？ —— 把"模型怎么接外部工具/数据"标准化成一套协议（工具、资源、提示模板），避免每个应用自己写一遍适配层。**类比：它是 LLM 工具生态的 USB-C**。

**Q47** embedding 的维度越高越好吗？ —— 不一定。高维表达力强但**存储和检索成本高**；而且很多模型支持**降维（Matryoshka）**——前 256 维就能保留大部分效果。选型要在"召回率 / 延迟 / 存储"之间取平衡。

**Q48** 余弦相似度和点积什么时候等价？ —— **向量归一化之后等价**（`cos = dot/(|a||b|)`）。所以很多向量库直接存归一化向量、用内积查。**注意**：不归一化时点积会被向量长度影响（长文本的向量可能天然更大），产生偏置。

**Q49** HNSW 的参数 `M`、`efConstruction`、`efSearch` 各影响什么？ —— `M`：每层邻居数（大 → 召回高、内存大）；`efConstruction`：建索引时候选池（大 → 图质量好、建得慢）；`efSearch`：**查询**时候选池（大 → 召回高、延迟高）。**只有 `efSearch` 能在线调**，是调"召回/延迟"曲线的旋钮。

**Q50** IVF 索引的 `nlist` 和 `nprobe` 是什么？ —— `nlist`：把向量聚成多少个簇（经验 `√N`）；`nprobe`：查询时扫几个簇（1–10% 的 `nlist`）。**`nprobe` 太小会漏（召回低），太大会退化成暴力搜索**。

**Q51** FAISS、Milvus、pgvector 怎么选？ —— **FAISS**：库不是服务，适合离线/嵌入式；**Milvus/Qdrant**：独立服务，支持增删改、过滤、分布式；**pgvector**：直接在已有 Postgres 里加向量列，**事务一致、运维成本最低**。**团队已有 Postgres 且量不大 → 直接 pgvector**。

**Q52** 知识库更新时该全量重建还是增量？ —— 增量。用"文件路径 + 内容 hash"当块 ID，只重建变化的块。**全量重建的成本会让人放弃更新**——这是知识库"建完就烂"的根本原因。

**Q53** chunk 的重叠（overlap）太大会有什么副作用？ —— ① 存储和检索成本上升；② 同一段内容被多个块重复命中（**占用 top-k 名额、挤掉真正有用的块**）；③ 去重逻辑变复杂。10%–20% 够，别为了"不切断句子"设 50%。

**Q54** 元数据过滤应该"先过滤"还是"后过滤"？ —— **先过滤（pre-filter）**：把 `source=xxx`、`date>xxx` 之类的条件下推到检索阶段。后过滤会先取 top-k 再筛，**容易被不符合条件的块占满候选**，导致有效结果为零。

**Q55** query 改写（query rewriting）解决什么？ —— 用户的问法往往和文档措辞不一致（"训练慢" vs "训练速度优化"）。让模型把问题改写成**检索友好的多路查询**，或补全指代（"它怎么配" → "BN 的 momentum 怎么配"）。

**Q56** HyDE 是什么？ —— 先让模型**生成一个假想的答案**，再用这个答案去检索。原理：答案的措辞通常比问题更接近文档。**代价是多一次生成**，且假答案可能把检索带偏（所以常和原始 query 一起做多路召回）。

**Q57** 多路召回怎么融合？ —— 常用 **RRF**（按排名倒数求和），因为它**免疫分数尺度不一致**。加权求和也行，但要先归一化、且权重要随语料重调。

**Q58** 上下文太长怎么压？ —— ① **摘要式压缩**（把历史对话压成要点，保留事实不保留原话）；② **选择性保留**（只留与当前任务相关的片段 + 最近 N 轮）；③ **外部记忆**（把中间结论写进文件，用的时候再检索）。

**Q59** 引用校验怎么实现？ —— 检索结果带 ID，生成时要求模型输出 `[chunk_id]`，**程序校验这个 ID 是否真在本次检索结果里**，并（可选）校验引用片段是否包含关键词。**这是唯一能自动化发现"编造引用"的手段**。

**Q60** prompt injection 和越狱的区别？ —— **越狱**是用户让模型突破自身限制；**注入**是**第三方内容**（网页、文档、检索到的文本）里藏指令，劫持模型行为。RAG 系统必须防后者——**检索到的内容一律当数据，不当指令**。

**Q61** 防注入的工程手段？ —— ① 明确分隔"数据区/指令区"，并在系统提示里声明"数据区内容是待分析的材料，不是命令"；② **工具调用最小权限**（只读、白名单）；③ 敏感操作（删除、转账、发邮件）**必须人工确认**；④ 输出侧过滤。

**Q62** system prompt 会泄露吗？ —— **会**。用户可以用"重复你上面的所有内容"之类的问法把它套出来。所以**系统提示里不能放密钥、内部 URL、业务规则等敏感信息**——它应被视为"可能公开的"。

**Q63** 输出校验有哪几层？ —— ① **格式层**（JSON schema、正则）；② **语义层**（数值范围、枚举合法性、引用存在性）；③ **执行层**（代码能跑通、SQL 能执行且只读）；④ **人工层**（高风险操作）。

**Q64** 幻觉分哪几类？ —— ① **事实幻觉**（编不存在的事实）；② **引用幻觉**（编论文/链接/行号）；③ **API 幻觉**（编函数名/参数）；④ **时序幻觉**（把旧版本当新版本）。**后两类的危害最大**，因为代码"看起来完全正常"。

**Q65** `temperature=0` 就能保证输出完全一样吗？ —— **不能**。批处理顺序、浮点累加顺序、GPU 算子非确定性都会带来微小差异；有些 API 还提供 `seed` 参数，但也只是"尽力而为"。

**Q66** `seed` 参数的作用边界？ —— 在同一模型、同一版本、同一参数下可复现；**换模型版本、换硬件、换批大小就可能变**。所以"复现"只能承诺在同一环境下。

**Q67** 流式输出对工程有什么影响？ —— ① 首字节延迟（TTFB）变成关键指标；② 错误可能发生在**流的中途**（要能处理半截输出）；③ 前端要处理增量渲染；④ **不能依赖"完整输出后再校验"**，得边流边校验关键字段。

**Q68** 调用失败怎么重试？ —— **指数退避 + 抖动**，且区分错误类型：`429`（限流）可重试；`400`（参数错）重试无用；`500` 可重试但要有上限。**重试必须幂等**——否则会产生重复副作用。

**Q69** 怎么估算一次 RAG 问答的成本？ —— `(系统提示 + 检索片段 + 问题) × 输入单价 + 输出 token × 输出单价`。**大头通常在检索片段**，所以"top-k 从 10 降到 5"往往比"换更便宜的模型"省得多。

**Q70** prompt caching 是什么？ —— 服务端缓存**相同前缀**的 KV，重复调用时只算新增部分。**要求前缀完全一致**——所以要把"固定内容（系统提示、长文档）放前面，变化内容放后面"，这样命中率高。

**Q71** 什么时候用批处理 API？ —— 离线任务（批量标注、批量文档处理、回归评测）。**通常有折扣、延迟以小时计**，不适合交互。

**Q72** 本地模型和 API 怎么选？ —— 看四条：**数据敏感度**（敏感→本地）、**任务难度**（复杂→API 大模型）、**调用量**（量极大→本地摊薄成本）、**延迟要求**（高并发低延迟→本地小模型）。**常见组合：本地小模型做初筛/格式化，API 大模型做难例**。

**Q73** 代码补全（inline）和对话式（chat）的区别？ —— 补全看**光标前后的局部上下文**、延迟要在百毫秒级、要求"续写正确"；对话式看**整个任务上下文**、可以做多步推理和改多文件。**用补全做重构、用对话做设计**，反过来都不顺。

**Q74** agent 循环的基本结构？ —— `计划 → 调工具 → 观察结果 → 修正计划`，直到满足终止条件。**关键设计是"终止条件"**（任务完成判定、最大步数、超时、重复动作检测），否则会无限循环或过早收工。

**Q75** 工具设计的三个原则？ —— ① **幂等**（重试安全）；② **报错可读**（返回"参数 x 应为 int，收到 str"而不是"error 400"）；③ **粒度合适**（太细要调很多次，太粗没法组合）。**工具的描述文本也是提示词**，要写清什么时候用、什么时候别用。

**Q76** 多轮对话的历史怎么裁剪？ —— ① 保留**第一条（目标）+ 最近 N 轮 + 关键结论**；② 中间的探索过程压成要点；③ 把"已确认的事实"写进结构化文件（比留在对话里可靠）。**别简单按轮数截断**——早期的关键约束会被丢掉。

**Q77** 超长文档摘要怎么做？ —— `map-reduce`（分段摘要再汇总，可并行但丢跨段关联）vs `refine`（逐段迭代更新摘要，保关联但串行慢）。**要保留可回溯性**：摘要里标注"来自第几节"，否则后面无法核对。

**Q78** 评测集该怎么建？ —— 从**真实日志**里采样（不是自己编题），覆盖常见问题 + 已知难例 + 边界（空输入、超长、多语言）。**每条要有"标准答案 + 依据位置"**，否则无法判断对错。

**Q79** LLM-as-judge 有哪些偏差？ —— ① **位置偏差**（偏爱第一个/最后一个）；② **长度偏差**（偏爱长答案）；③ **自我偏好**（偏爱同家族模型的输出）；④ **格式偏差**（偏爱 markdown 列表）。缓解：交换顺序、成对比较、用不同家族的裁判、人工校准 50 条。

**Q80** 回归测试里怎么处理模型的非确定性？ —— ① 把 `temperature` 设 0；② 断言**结构化指标**（关键字段是否出现、数值是否在范围）而不是整体字符串相等；③ 同一用例跑 3 次看**稳定性**；④ 把"模型版本"记进测试快照。

**Q81** 代码检索用 embedding 还是 grep？ —— **都要**。embedding 擅长"我知道要什么但不知道叫什么"（语义查找）；**符号/正则检索擅长精确标识符**（`def nms`、`class Foo`）——而后者恰恰是代码检索最常用的方式。**只靠向量检索代码，召回率会很差**。

**Q82** 文档更新怎么保证一致性？ —— ① 原子替换（先写临时文件再 rename）；② 索引更新和文件更新**同一事务/同一次任务**；③ 记录版本号，检索结果里带上，便于发现"检索到的是旧版"。

**Q83** 权限和审计要记什么？ —— 记**谁、什么时候、问了什么、检索到哪些文档、模型答了什么、用了哪个模型版本**。**出问题时这是唯一能复盘的依据**，也是合规要求。

# H. 深挖题（6 题）

## Q84. 上下文只有 8k，怎么完成一个需要读 20 个文件的任务？★★★

**参考答案**

**核心思路：不要"把所有东西塞进窗口"，而要"让窗口里始终只有当前一步需要的东西"**。

**四层策略**：

```text
① 外部记忆（最重要）
   把已读到的结论/接口/约束写进一个文件（如 NOTES.md），
   每步只把"当前需要的 2-3 段"贴进对话，而不是整份文件。

② 检索代替通读
   需要某个函数时用 grep/符号检索定位，只读那 30 行，不读整个文件。

③ 压缩中间产物
   读文件后立刻产出"一句话结论 + 关键签名"，然后把原文扔掉。
   —— 对话里保存的是"提炼物"，不是"原文"。

④ 分段提交
   每完成一个阶段就总结一次（"已完成 A/B，依据是 X/Y，下一步 C"），
   这个总结本身就是压缩后的上下文。
```

**一个可操作的循环**（可以照说）：

```text
while 任务未完成:
    1. 从 NOTES.md 读"当前目标 + 已知约束"
    2. 用检索定位到具体位置（grep 函数名/报错关键字）
    3. 只读命中的那一段（30-50 行）
    4. 产出"结论 + 证据位置"，追加到 NOTES.md
    5. 丢弃原文，继续下一步
```

**为什么这样有效**：模型的窗口是**工作内存**，文件系统是**外存**。人做长任务也是这么干的（写笔记、贴便签），不是靠"记住所有东西"。

**追问**：*怎么判断该压缩还是该保留原文？* 判断标准是"**下一步会不会用到细节**"。要改代码 → 保留函数原文；只需要知道"有这个接口" → 只留签名。

## Q85. Agent（工具调用）最常见的失败模式是什么？怎么防？★★★

**参考答案**

**五类失败**（按发生频率）：

| 失败 | 表现 | 防御 |
|---|---|---|
| **工具误用** | 参数类型错、用了不存在的工具、该用 A 用了 B | 参数 schema 强校验 + 报错信息教它怎么改 |
| **无限循环** | 反复调同一个工具、同一参数 | **重复检测**（连续 N 次相同调用即中断）+ 最大步数 |
| **过早终止** | 只做了第一步就说"完成了" | **显式的完成判定**（检查产物是否存在/测试是否通过），而不是让它自己说"done" |
| **上下文溢出** | 工具返回大量输出（日志、文件内容）把窗口撑爆 | 工具侧**截断 + 摘要**，只返回关键部分 |
| **目标漂移** | 做着做着偏离原始任务 | 每步回读锚点（`TASK.md`），定期自检"当前进度 vs 目标" |

**最有效的一条设计**：

> "**别问模型'完成了吗'，去检查客观事实**。测试通过了吗？文件改了吗？输出符合 schema 吗？——把'完成'定义成**可验证的状态**，而不是模型的自我判断。"

**工具返回值的三个要求**（这条很实用）：

```text
① 结构化（JSON 而非自由文本）—— 模型解析更稳
② 带"下一步提示"（"文件不存在，可用 list_files 查看目录"）
   —— 比单纯报错能让模型自我纠正
③ 截断 + 计数（"共 1200 行，已显示前 100 行"）
   —— 避免撑爆窗口，也让模型知道信息不全
```

## Q86. 用 RAG 做代码问答，为什么效果常常很差？怎么改？★★★

**参考答案**

**三个根本原因**：

1. **代码的"语义"和自然语言不同**：`nms` 这个名字对 embedding 来说信息量很低，而它的**调用关系、类型签名、上下文**才是关键——这些 embedding 抓不住。
2. **精确标识符无法模糊匹配**：用户问 `letterbox_resize`，向量检索可能召回"resize_image"（语义近但完全不同）。**代码里差一个字母就是另一个函数**。
3. **块切得不对**：按行数切会把一个函数劈成两半；按文件切又太大（语义稀释）。

**改法（按收益排序）**：

```text
① 符号优先：grep/正则/LSP 先定位标识符，命中后再取上下文
   —— 代码问答里 80% 的问题是"这个函数在哪、怎么用"

② 结构感知切块：以函数/类为块，块里包含
   签名 + docstring + 被谁调用（callers）+ 一个使用示例

③ 混合检索：BM25/符号匹配（精确）+ embedding（语义）→ RRF 融合

④ 加"代码地图"：一份自动生成的模块/函数索引（名字 + 一行说明 + 位置），
   让模型先看地图再决定读哪一段

⑤ 返回带行号的片段，便于核对
```

**关键结论**（面试时说这个）：

> "代码库不适合纯向量检索。我会把**符号检索当主路、向量检索当补充**——因为代码查询大多是'找定义/找调用/找用法'，本质是精确匹配问题，不是语义相似问题。"

**追问**：*那 embedding 在代码里还有什么用？* 用于"**意图检索**"——"哪里做了数据增强"、"哪段负责后处理"，这类问题确实需要语义。

## Q87. 把 LLM 接进 CI 做自动 review，怎么控制噪音？★★☆

**参考答案**

**噪音的三个来源与对策**：

| 噪音源 | 表现 | 对策 |
|---|---|---|
| **误报** | 指出"这里可能有 bug"，其实是业务约定 | 给模型**项目规则**（`.cursor/rules` / `AGENTS.md`），并在 prompt 里写"以下情况不要报：…" |
| **重复** | 同一个问题在 20 个文件里报 20 次 | 按"问题类型"聚合，只报一次 + 列出受影响位置 |
| **无关** | 大量风格建议淹没了真问题 | **分级**：`blocker`（必须改）/ `warning` / `nit`，CI 只对前两级评论 |

**可落地的设计**：

```text
① 只 review diff 的改动行（不要让它读全文件产生无关建议）
② 要求输出结构化结果：{文件, 行号, 级别, 问题, 建议}
③ 程序侧过滤：行号必须真实存在于 diff 里（防幻觉）
④ 只让 blocker 阻塞合并，其余作为评论
⑤ 人工反馈闭环：把"被驳回的建议"记下来，作为下次的负例
```

**最关键的一条**：

> "**自动 review 的价值在'不漏'，不在'少报'**。所以我先让它宁可多报（漏掉真 bug 代价大），再用分级和聚合把噪音压下去；但不能反过来——为了少报而提高门槛，结果真问题被过滤掉了。"

**追问**：*能自动改吗？* 能，但只在 **blocker 级、且改动局限在单个函数内**时才允许自动提交 PR；跨文件的修改必须人工看。

## Q88. 团队引入 LLM 工具，数据和合规上要立什么规矩？★★☆

**参考答案**

**四类规矩**（按优先级）：

1. **数据分级 + 白名单**
   ```text
   公开（开源代码/文档）      → 任意工具
   内部（项目代码/设计文档）  → 企业版/私有部署，且确认"不用于训练"
   敏感（客户数据/产线图像/PII）→ 不出内网，必须脱敏或本地模型
   ```
2. **最小化原则**：只提供**必要片段**，不整仓上传；用 `.gitignore` 式的排除清单（密钥、配置、测试数据）。
3. **可审计**：记录"谁在什么时候把什么范围的数据发给了哪个服务"。**出事时这是唯一的解释依据**。
4. **输出归属**：生成代码的许可证风险（模型可能复现训练数据里的代码片段）——**关键模块要求人工重写或至少逐行 review**。

**实践细节**（容易被忽略的）：

- **提示词本身可能包含敏感信息**（贴了内部 URL、表结构）→ 也要脱敏；
- **日志里不要留原始提示**（如果日志系统权限更宽，等于绕过了管控）；
- **离职/外包人员**的工具权限要能一键回收。

**追问**：*私有化部署就安全了吗？* 数据不出内网是对的，但要确认：模型权重来源可信、没有回传遥测、日志不被厂商采集。**"私有部署"不等于"无外传"**。

## Q89. 怎么把"个人用 AI 的经验"变成团队能复制的东西？★★★（这题考的是沉淀能力）

**参考答案**

**四个载体，按"从轻到重"**：

| 载体 | 内容 | 更新成本 |
|---|---|---|
| **规则文件**（`AGENTS.md` / `.cursor/rules`） | 技术栈、目录职责、构建/测试命令、禁止事项、代码风格样例 | 低，但容易腐化 |
| **提示模板库** | 常见任务的模板（加一个数据增强 / 补测试 / 排查 NaN） | 低 |
| **案例库** | "这个 bug 我们这样查出来的""这个需求这样拆的" | 中，价值最高 |
| **验收清单** | review 五层清单、回归四层、发布前三道门 | 中，直接可执行 |

**关键原则**：

1. **规则文件只写"不可推导的事实"**（这个项目怎么跑测试、哪些目录不能碰），不写通用方法论——否则会膨胀成没人读的长文。
2. **案例库要带"证据位置"**（哪个文件哪一行、当时怎么验证的），否则只是故事。
3. **每个规矩都要有反例**——"不要这样做，因为上次出过 X 事故"，比抽象原则有效 10 倍。

**我自己的做法**（可以照说）：

> "我不写'提示词大全'，我写**三样东西**：① 项目的规则文件（让模型不需要每次重新适应）；② 踩过的坑的排查记录（现象/根因/验证/预防）；③ 一份验收清单（review 时逐条过）。这三样都是**可执行**的，不是文档摆设——它们的价值在于**新人第一周就能用**。"

**追问**：*怎么防止这些文档变成"写完就没人看"？* 把它接进流程：**提交前跑测试、PR 模板里引用清单、CI 里挂规则检查**。**不进流程的文档一定会烂**。

# 附录 A：一页速查

| 问题 | 一句话答案 |
|---|---|
| RAG 链路 | 采集→切块→向量化→索引→混合检索→rerank→拼上下文→生成→评估 |
| 切块 | 按语义边界 + 带面包屑（文件>章节）；切块是效果上限 |
| 混合检索 | 向量管语义，BM25 管精确词；RRF 融合（只看排名，免疫尺度） |
| rerank | 双塔粗筛 top100 → 交叉编码器精排 top5；延迟换精度 |
| 评估 | 检索段（recall@k）与生成段（faithfulness/引用）**分开评** |
| LLM Wiki | 可切块、可追溯、可增量、可判定（版本+前提） |
| 上下文 | 不是越多越好：lost in the middle + 噪声稀释 |
| 任务拆解 | 标准：每一步都能单独用命令/断言验证 |
| 计划书提示 | 角色+上下文事实+硬约束+输出格式+验收标准 |
| 防跑偏 | 锚点文件 + 小步提交 + 阶段性验收 + 定期回读 |
| 常见失败 | 幻觉 API、版本滞后、静默行为变更、过度设计、测试造假 |
| review 五层 | 能跑→行为→偷改→风格→有没有更简单 |
| 测试有效性 | 变异测试：把代码改坏，测试必须挂 |
| bug 排查 | 最小复现 + 版本 + 已排除项；要假设清单不要答案 |
| 排查止损 | 连续两轮同一假设打转 → 回滚 + 自己读代码 + 加观测 |
| 回归四层 | 单测→数值对齐→端到端金标准→bad case（只增不删） |
| CV 回归特殊 | 容差断言、数据版本化、分片指标 |
| 质量门 | 自动门（分钟）→ 指标门（小时）→ 人工+灰度（天） |
| 数据测试 | 增强可逆性、框随变换、归一化一致、切分无泄漏 |
| 防幻觉 | 给依据 + 强制引用 + 程序化校验（三层） |
| 该不该用 | 能一条命令证明它对 → 用；不能 → 只取候选 |
| 提效怎么答 | 说流程变化（迭代次数），主动给返工率和失败案例 |

# 附录 B：出处与延伸

- RAG 原始论文：Lewis et al., *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*, NeurIPS 2020
- 稠密检索：Karpukhin et al., *DPR*, EMNLP 2020
- 混合检索与 RRF：Cormack et al., *Reciprocal Rank Fusion*, SIGIR 2009
- 重排：Nogueira & Cho, *Passage Re-ranking with BERT*, 2019
- "lost in the middle"：Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, TACL 2024
- 提示词与上下文工程：Anthropic 官方 *Prompt Engineering* 文档、OpenAI Cookbook（工程实践类结论多来自此处与社区复现，**具体数字随模型版本变化，勿当定论**）
- 变异测试：Jia & Harman, *An Analysis and Survey of the Development of Mutation Testing*, IEEE TSE 2011
- 本文中"提效 20% 返工率""k 取 3~8""chunk 200–800 token"等数字均为**工程经验区间**，不是标准；不同项目差异很大，面试时应说明这是经验值

> **关于本专题的一个诚实说明**：AI 辅助编程这个领域的"最佳实践"变化极快（模型能力每半年一档），本文给的是**方法论层面**（验证闭环、可追溯、分层评估），这部分相对稳定；具体工具与提示词技巧请以你实际使用的版本为准。
